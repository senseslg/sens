# 记录维护指南

用于决定一条信息应该写到哪里，以及更新到什么程度。

## 文件职责

| 文件类型 | 保存什么 | 不保存什么 |
|---|---|---|
| `PROJECT_OVERVIEW.md` | 长期目标、范围、结构、当前稳定状态 | 逐日过程和大量细节 |
| `PROJECT_ITERATION_LOG.md` | 按时间排列的重要变化摘要 | 详细背景和完整操作步骤 |
| `records/projects/*.md` | 单个项目的当前状态、决定、风险和下一步 | 与项目无关的通用规则 |
| `records/daily/*.md` | 需要跨天延续的当日重点 | 每一次聊天或琐碎动作 |
| `records/meetings/*.md` | 会议结论和行动项 | 无结论的逐字稿 |
| `reference/*.md` | 稳定方法、规范和专题知识 | 只发生一次的临时情况 |
| `RUNBOOK.md` | 本机验证过的命令和环境问题 | 稳定业务背景 |

## 更新顺序

1. 更新最接近事实来源的项目、会议或每日记录。
2. 如果稳定状态改变，再更新 `PROJECT_OVERVIEW.md`。
3. 如果变化值得以后追溯，在迭代日志顶部增加一行。
4. 如果形成可重复方法，更新 `reference/` 和 `SKILL.md`。

## 迭代日志格式

```markdown
- **vX.Y.Z** YYYY-MM-DD — 一句话说明发生了什么以及它为何重要
```

- 最新记录放在顶部。
- 一次变化尽量保持一行。
- 细节放到对应文件，并在需要时从日志链接过去。

## 项目记录要求

项目主记录至少应说明：

- 目标和完成标准
- 当前状态
- 已确认范围
- 重要决定
- 当前行动项
- 风险、依赖或阻塞
- 最近更新时间

项目主记录应呈现“当前有效状态”。历史变化由 Git 和迭代日志承载，不要在正文里保留多套互相冲突的旧结论。

## 命名规则

- 项目：`records/projects/<short-name>.md`
- 每日：`records/daily/YYYY-MM-DD.md`
- 会议：`records/meetings/YYYY-MM-DD-<topic>.md`
- 专题：`reference/<topic>.md`

文件名使用简短、稳定、可检索的英文小写加连字符；正文可以使用中文。

## 质量检查

- 日期、状态和下一步是否明确。
- 是否把建议误写成决定。
- 是否存在重复且不一致的主要事实。
- 是否包含无意提交的敏感信息。
- 链接是否指向真实文件。
- 记录是否足以让下一次沟通恢复上下文。
