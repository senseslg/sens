# Google Cloud 降本计划

> 历史初步计划。当前以 [2026-10-24 完整核查清单](COST_OPTIMIZATION_CHECKLIST_2026-10-24.md) 为准，已补齐负载、两年前对象容量、GKE 净费用及 Cloud SQL 缩容条件；下方预算不是已验证节省。

更新日期：`2026-10-17`。目标是将 `cambodian-express` 每月账单从税后约 `$4,000` 降至税后 `$2,000` 以内，同时保留生产业务的可恢复性。

## 结论

- 2026 年 9 月完整账单为税前 `$3,704.77`、税费 `$370.48`、税后 `$4,075.25`，实际税率约 `10%`。
- 税后 `$2,000` 对应税前上限约 `$1,818.18`；相对 9 月需每月减少至少 `$1,886.59` 税前费用。
- 仅关闭几台小型 VM 无法达标。Cloud SQL、Compute Engine、Geocoding、Translate 和 Networking 合计占 9 月税前费用约 `90.5%`，必须同时治理。
- 先停用已确认无业务流量的 UAT/旧入口，再处理 API 调用和 Cloud SQL；生产数据库、`wms-db`、`ce-lb`、TMS 与 OTWMS 不应直接关闭。

## 资源处置顺序

### 第一批：低风险、先确认后停

| 资源 | 当前状态 | 建议 | 前置检查 |
|---|---|---|---|
| `tms-uat` | E2 medium，100 GB 磁盘，独立 LB | 无人使用时停机，保留短期恢复窗口；随后评估删除 LB 与磁盘 | 最近 30 天登录、HTTP 请求、发布与数据库连接 |
| `otwms-uat` | E2 medium，30 GB 磁盘，独立 LB、1 GB Redis | 无人使用时同时停 VM 与 Redis；LB 在观察期后撤销 | 测试团队确认、入口流量、任务与回调 |
| `toucha-uat` | E2 standard 2，300 GB balanced disk，独立 LB | 优先核实是否仍需运行；若需要，先按工作时段启停；官方建议可降为 1 vCPU/约 8 GB，每月约省 `$17.98` | 业务负责人、磁盘实际数据、近 30 天访问 |
| `nacos` 磁盘 | 100 GB、未挂载 | 核对恢复用途后做最终快照并删除；官方建议预计约省 `$4.74/月` | 快照、旧实例和 Nacos 当前服务位置 |
| `tms-group` | 托管实例组目标数 0 | 若已由独立 TMS 实例取代，清理旧模板、健康检查和残留 LB 关系 | 当前 LB 后端、回滚用途 |
| `cluster-1` | GKE 集群运行，节点组目标数 0 | 核实无工作负载后删除空集群及关联配置 | namespaces、workloads、持久卷、Ingress |

### 第二批：需要迁移或容量验证

| 资源 | 当前状态 | 建议 | 不能直接做的原因 |
|---|---|---|---|
| `wms-server` | E2 small、600 GB；`cewms.service` 已停，但 `cp.service` 仍运行 | 迁移 `cp` 后关机观察，再将 600 GB 系统盘迁到更小磁盘或删除 | 关 VM 会同时中断 `cp`；仅关机仍会收磁盘费 |
| `tms-db` | 8 vCPU、52 GB RAM、1,253 GB SSD；约 714 GiB 为接口审计表 | 先建立日志保留策略和克隆回收演练，再以真实 CPU/内存峰值评估 4 vCPU/26 GB 或中间规格 | Cloud SQL 磁盘不能原地缩小；直接降配可能导致生产抖动 |
| TMS 生产 | C2 standard 8，JVM `Xms/Xmx 24g` | 先解决 OOM、HTTP 阻塞和 FD 风险，再压测较小规格或调整 JVM | 当前已有稳定性事故，直接降配会放大风险 |
| OTWMS 生产 | C2 standard 4，50 GB | 先修复 DEBUG/stdout 日志风暴和镜像固化，再依据 30 天峰值评估降配 | 当前磁盘事故会污染利用率和重建频率 |
| `wms-db` | E2 highmem 4、500 GB，多项共享平台服务 | 先分清 Jira、Bitbucket、Jenkins、MySQL、Redis 等依赖，再评估非工作时段停 Jenkins 或服务拆分 | 单机承载多项关键平台，直接关机会造成广泛中断 |

### 第三批：应用和网络治理

1. **Geocoding**：按 API key、调用来源和接口拆分用量；为测试 key 设置每日配额；对重复地址做坐标缓存；禁止页面输入每次击键直接请求。目标从 `$673.77` 降至 `$150`。
2. **Translate**：确认 9 月 1,486 万次调用的来源，建立内容哈希缓存、批处理和失败重试上限；生产与测试 key 分离并设预算告警。10 月当前费用已明显下降，但仍以 `$50` 月上限管理。
3. **负载均衡**：当前 16 个全局地址、33 条转发规则，多套 UAT/旧服务各自占用 HTTP 与 HTTPS 规则。停用 UAT 后同步清理 forwarding rule、target proxy、URL map、backend service、health check 和保留 IP，避免只关 VM 仍继续付费。
4. **Cloud Storage**：按 bucket 统计存储量、下载流量和对象年龄；对日志、构建物与临时文件配置生命周期；对仍在使用的前端 bucket 保留。
5. **Memorystore**：`otwms-uat` 停用后可减少 1 个 1 GB Basic 实例；生产 `redis` 与 `tms-redis` 先核实内存、连接与持久化需求。

## 执行闸门

每个停用候选按以下流程处理：

1. 确认业务负责人、域名、调用方、定时任务和最近 30 天流量。
2. 记录当前配置、磁盘/数据库备份和恢复命令。
3. 先停止或缩容，观察 7 天；生产入口至少观察一个完整业务周期。
4. 检查错误率、告警、客服反馈和关联账单。
5. 观察通过后再删除资源；删除动作必须单独获得用户明确授权。
