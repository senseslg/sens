# Public Bandwidth Sizing Plan

## 当前建议

| 场景 | 建议公网带宽 | 说明 |
|---|---:|---|
| 立即验证 | `10 Mbps` | 从 3 Mbps 临时升级，用同一客户端、同一页面做前后 A/B 测试 |
| 暂无 CDN、日常低到中等流量 | `20 Mbps` | 当前阶段较合适的正式起点，可显著改善首次加载和少量并发 |
| 暂无 CDN、促销或较多图片并发 | `30–50 Mbps` | 只适合作为过渡；应同时监控出口峰值和费用 |
| 已使用 CDN / OSS | 源站 `5–10 Mbps` 起步 | 静态资源和图片由边缘分发，ECS 主要承载 HTML、API 和回源 |

不建议现阶段直接购买 `100 Mbps`。当前站点还存在 Nuxt/Next.js 部署不一致、大型 JS 未压缩和 HTTP/1.1 等问题，单纯加带宽会掩盖这些问题，也不能解决上游 API、数据库或 SSR 延迟。

## 当前页面的理论差异

线上首页引用的 `/_nuxt/` 资源标称总量约 `1.04 MB`，其中最大 JavaScript 约 `613 KB`，当前未压缩。忽略协议、并发、图片和网络损耗时：

| 带宽 | 1.04 MB 理论传输时间 | 613 KB 理论传输时间 |
|---:|---:|---:|
| 3 Mbps | 约 2.8 秒 | 约 1.6 秒 |
| 10 Mbps | 约 0.8 秒 | 约 0.5 秒 |
| 20 Mbps | 约 0.4 秒 | 约 0.25 秒 |
| 50 Mbps | 约 0.17 秒 | 约 0.10 秒 |

这些只是吞吐下限，真实体验还会受到 HTTP/1.1 连接并发、TLS、服务器处理、图片、API 和用户所在地区影响。

## 推荐实施顺序

1. 临时将固定公网带宽从 3 Mbps 提升到 10 Mbps。
2. 分别记录 3 Mbps 与 10 Mbps 下的首页首次加载、重复加载、最大 JS 下载时间和公网出口峰值。
3. 同时为 JavaScript 启用 gzip/Brotli，并启用 HTTP/2。
4. 如果 10 Mbps 明显改善且出口经常接近上限，短期升至 20 Mbps。
5. 将 `/_nuxt/` 或未来的 `/_next/static/`、商品图片迁移到 OSS + CDN。
6. CDN 稳定后，根据源站 P95 峰值重新下调或保留 ECS 带宽，不再靠固定带宽承载全部图片流量。

## 扩容判断标准

满足以下任一项时再向上扩容：

- 阿里云监控显示访问慢时公网出方向持续达到配置带宽的 `70%–80%` 以上。
- 10 Mbps A/B 测试的页面完成时间比 3 Mbps 明显下降。
- 高峰期间排除 CPU、数据库和上游 API 后，下载阶段仍明显排队。

如果出口带宽没有接近上限，加到 20 Mbps 或 50 Mbps 通常不会解决问题，应继续排查应用处理时间、Nuxt/Next.js 部署、外部 API 和数据库。

## 计费与线路注意事项

- 当前固定带宽适合流量相对稳定、需要明确带宽保障的业务。
- 阿里云支持对包年包月实例临时升级固定公网带宽，可用于短期 A/B 验证。
- 若主要用户位于中国内地，香港地域还应评估 BGP 精品线路；提高 Mbps 不能单独解决跨境路由和时延问题。
- 所有升配都属于计费变更，实施前应在控制台确认价格和生效周期。
