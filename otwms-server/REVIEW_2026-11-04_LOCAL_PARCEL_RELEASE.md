## 优先修正项

### F01 · P1 · 新增费用与入库回调绕过应用鉴权

位置（OTWMS `6ed4c29b7`）：`otwms/external/api/ExternalApi.java:320–327`；现有鉴权链为 `AbstractExternalAPI.run`、`TokenCompositionInterceptor.preHandle`、`PublicApiInterceptor`。

两个新方法直接调用 manager，没有进入原有的合作方 Authorization 校验。父类的自定义拦截器实际为空；组合拦截器发现该注解后不会再调用默认 Token 校验。Manager 仅凭运单号更新费用或业务状态，也没有合作方归属限定。故缺陷不只涉及本土业务，处理器能找到的其他来源订单也在修改范围内。

建议：恢复合作方鉴权、授权来源与订单归属检查；费用数值校验和状态机约束必须在服务端执行。代码链路已核对，但公网可调用性未主动实测；没有使用真实单号探测写接口，也没有认定发生过滥用。

### F02 · P1 · 批量揽件入库把“至少一单已入库”当成整批成功

位置：`tms/service/impl/TmsShipmentServiceImpl.java:332–361`。

查询只要求存在一条 `PICKUP` 状态运单，就对原始请求的全部订单添加日志、构造 CCSL 回传；当 TMS 返回失败时还把总结果改成成功。例：A 之前已入库、B 本次因校验失败未入库，只要查询命中 A，B 也可能被当作成功通知 CCSL。已有的历史状态不证明本次扫描成功。

建议：保留逐单成功/失败结果，只处理已确认成功的子集；明确区分本次成功与历史已完成。该路径不限于新增本土单，需回归既有批量扫描。未在生产制造混合成功/失败批次。

### F03 · P1 · 入库回调先改状态，忽略下游失败，仍返回成功

位置：`otwms/external/manager/ExternalManager.java:475–504`。

`ccslPhnInbound` 在 TMS 扫描前无条件写 OTWMS 业务状态并保存成功推送记录；没有检查 `scanUpdate` 返回 Map 的 `success`，异常也只记录日志，最终始终成功。即使 TMS 拒绝、超时或扫描后处理失败，CCSL 也无法按需求将本次入库标为失败。同时，迟到或重复回调没有前置状态限制，存在将已推进订单回写为揽件入库状态的风险。

建议：先校验来源及允许状态，再执行扫描并检查真实结果；失败须返回可识别失败并保留可补偿记录。重复调用应幂等。不要在扫描完成前记录成功。

### F04 · P1 · 建单业务失败被记成功，揽件回调也只看 HTTP 状态

位置：`otwms/business/order/components/CcslOrderCreateHandler.java:118–129、212–223`。

创建请求只要未抛异常，就无条件标记成功；回调只检查 HTTP 200，未检查业务 `code/success`。CCSL 业务校验错误通常也通过 HTTP 200 返回。

**实证**：只读查询生产 `tms_uat.push_records` 的一个发布后样本，结果为 `code=400, success=false, msg=System Error`，但 `status=1`（成功）。不保存该样本单号。既有失败重试仅选择 `status=2`，因此该失败不会被自动补偿。前次调查的 5 次业务失败不能据此直接假设全部都已逐条核验。

建议：同时检查 HTTP、业务码与成功标记；只有业务接受才记成功。失败需留全量、可恢复的请求。

### F05 · P1 · 新增请求进入旧重试中心后会重发到错误接口

位置：新处理器写 `push_records` 的 `SHIPMENT_CREATED/PICKUP_INBOUND` 记录；`tms/manager/PushRecordsManager.java:77–90、123–128`。

重试查询没有按通知类型或原始接口区分，发送地址固定为 `/api/external-api/order-status-feedback`。新增的创建订单请求和取件请求一旦因网络异常留下 FAIL，重试会把其原始 JSON 发到状态反馈接口。该 JSON 不是状态反馈结构，无法正确补偿。新处理器还将请求截断到 1999 字符，长地址场景可能截断 JSON。

建议：记录并按事件类型选择目标接口、环境和鉴权方式，持久化完整可重试报文；重试严格按业务成功判定。旧重试器本身未在本次变更，但新增请求类型进入它导致兼容风险。本次没有执行重推。

### F06 · P1 · 到付、COD付与预付没有保留正确的收款语义

位置：`CcslOrderCreateHandler.java:133–140、178–202`；CCSL 对端 `external/manager/ExternalManager.orderPickupCallback`。

发送端把“到付”和“COD付”都映射成 CCSL 到付；取件报文一律将货款、运费、保价、包材相加为 `sum`，没有根据支付方式计算收件人应收。对端直接保存报文 `sum`。需求明确 COD付从货款抵运费，不能额外向收件人加收运费；预付/记账也不应按到付方式计算应收。

例：COD 100、运费 2、无其他费，COD付的收件人应收为 100，而该公式为 102。此为代码及需求层面的金额冲突，未认定已有实际错收；CC/CE 前缀在此处理器会跳过，真实触发还受 TMS 负责的回调路径影响。

建议：先统一“费用明细、收件人应收、客户结算”三者定义，再按四种支付方式分别验证。仅把 COD付映射到 CCSL 到付不能保留原业务含义。

### F07 · P2 · 收件城市字段未被对端接收，市区信息丢失

位置：`CcslOrderCreateHandler.java:77–79`；CCSL `external/api/ExternalApi.java:282–290` 及 `ExternalReqDTO`。

OTWMS 发送 `cityCode`、`districtCode`；当前 CCSL DTO 没有 `cityCode`，而 `districtCode` 的约定是 L3 城市码，CCSL 数据库的 `district` 本来表示城市、`community` 才表示区。直接同名映射使城市被忽略，区码可能被放错层级或解析失败后留空。

**实证**：已知测试样本的请求含城市参数，但 UAT 订单的 `district`、`community` 都为空。自动分拣要求城市与社区编码，该问题可能导致分拣降级到省级或无法精确路由。

建议：明确发送/接收双方 L2/L3/L4 字段契约，并用金边和外省地址核对落库及分拣码；不能只以建单成功验收地址正确。

### F08 · P2 · 创建出的订单与包裹不满足同号、同业务类型要求

位置：`CcslOrderCreateHandler.java:67–68`；CCSL `external/manager/ExternalManager.createOrder:156–176、224–241`。

发送端用 OTWMS 订单编号作 `expressNo`、用 CE 运单号作 `shipmentCode`。对端将两者分别保存为包裹单号和运单号，并只把订单设置成本土类型，没有同步设置包裹业务类型。

**实证**：同一 UAT 样本的订单 `business_type=2`、包裹 `business_type=1`，且包裹单号与运单号不等。需求明确订单/包裹都为本土、包裹单号与运单号一致。风险涉及按包裹扫描、类型筛选、轨迹与国际/本土业务隔离，需两端共同修正，不能只改 OTWMS 地址。

## 尚需联调确认的依赖

- 新处理器主动跳过全部 CC/CE 前缀取件通知，假定 TMS 已负责。新增单也可能是 CE 前缀；必须以实际 TMS 生产版本验证该回调覆盖本土单及四种支付方式，不能只运行“应跳过”单元测试就证明全链路正确。现有 TMS 发布记录快照不等于本次的运行版本核验。
- 新增 `ccslBooking` 每次都插入创建轨迹，无论订单是否已经存在；重复推送可能形成重复创建轨迹，并存在使用 CCSL 编码而非匹配到的 OTWMS 运单号的情况。尚未主动构造重复请求。
- `ccslFeeUpdate` 只写 OTWMS 订单费用，没有同步 TMS 收入/成本、支付明细；应明确哪套数据为计费与结算依据，再验证金额回写一致性。没有制造费用变更。
- 新创建处理器在建单请求线程同步调用 HTTP，没有显式连接/读取超时；需离线故障注入验证慢 CCSL 对建单接口的影响，不在生产压测。
